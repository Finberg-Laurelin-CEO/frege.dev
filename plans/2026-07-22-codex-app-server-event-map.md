# Codex App Server event map for Live Run Rooms

Date: 2026-07-22

Installed binary: `codex-cli 0.144.6`

Transport: JSON-RPC over stdio (`codex app-server --stdio`)

Gate result: **PASS on focused attempt 1**

## Spike procedure

The scratch client sent `initialize`, then `initialized`, `thread/start`, and
`turn/start`. The first prompt returned `SPIKE_OK` without tools. A second
read-only probe ran `pwd` once to capture command item shapes. Both turns emitted
live notifications and completed normally. The scratch script stayed outside the
repository and is not committed.

The installed-version schema was also generated with:

```sh
codex app-server generate-json-schema --out <temporary-directory>
```

## Client methods verified

| Method | Required fields used or verified |
| --- | --- |
| `initialize` | `clientInfo.name`, `clientInfo.version`; response reported server version `0.144.6` |
| `initialized` | notification with empty params after initialization succeeds |
| `thread/start` | optional `cwd`, `ephemeral`, `approvalPolicy`, `sandbox`; response contains `thread.id` |
| `turn/start` | `threadId`, `input[]`; response contains `turn.id` |
| `turn/steer` | schema-verified: `threadId`, `expectedTurnId`, `input[]` |
| `turn/interrupt` | schema-verified: `threadId`, `turnId` |

## Notifications observed live

| Codex notification or item | Observed payload cue | Frege mapping |
| --- | --- | --- |
| `thread/started` | `params.thread.id` | `run.live.started` once per bridge session |
| `turn/started` | `params.threadId`, `params.turn.id` | bridge state only; include ids on later event payloads |
| `item/started`, `item.type=userMessage` | user input item | no live ledger event; the directive or session input already records the actor action |
| `item/started`, `item.type=agentMessage` | empty text plus `phase` | begin buffering message deltas |
| `item/agentMessage/delta` | `itemId`, `delta` | `run.live.agent_message` with delta and ids |
| `item/completed`, `item.type=agentMessage` | authoritative full `text` and `phase` | flush/finalize `run.live.agent_message`; do not duplicate already-flushed text |
| `item/started`, `item.type=commandExecution` | `item.id`, `command`, `cwd`, `status` | `run.live.command.started` |
| `item/completed`, `item.type=commandExecution` | `aggregatedOutput`, `exitCode`, `durationMs`, final `status` | `run.live.command.finished` |
| `turn/completed` | final turn `status`, ids, timing | turn state only; the room remains live for another turn |
| `thread/status/changed` | active or idle state | connection state only |

The App Server also emitted hook, MCP-startup, token-usage, rate-limit, and remote
control status notifications. Live Run Rooms ignores those for v1 because they are
not part of the shared work timeline.

## Installed-schema mappings not exercised by the harmless probes

These exact names come from the JSON schema generated by the installed binary.
They are safe to implement against, but the event map distinguishes them from the
notifications observed in the two live probes.

| Codex method/request | Frege mapping or bridge action |
| --- | --- |
| `item/fileChange/patchUpdated` | `run.live.file_change` |
| `item/fileChange/outputDelta` | append/coalesce into the matching `run.live.file_change` payload |
| `item/commandExecution/outputDelta` | append/coalesce into the matching command payload; the completed item is authoritative |
| `item/commandExecution/requestApproval` | `run.live.approval.requested`; retain the JSON-RPC request id and `approvalId ?? itemId` |
| `item/fileChange/requestApproval` | `run.live.approval.requested`; retain the JSON-RPC request id and `itemId` |
| `item/permissions/requestApproval` | `run.live.approval.requested`; unsupported remote resolution must remain denied/terminal-local |
| `thread/closed` | `run.live.ended` |

Command and file approval responses are `{ "decision": "accept" }` or
`{ "decision": "decline" }` for the v1 remote path. The bridge must never send
`acceptForSession`, policy amendments, or any default approval. It may answer only
the exact outstanding JSON-RPC request whose stored approval id matches the Frege
directive.

## Stable bridge rules

- Frege stores only the stable `run.live.*` vocabulary; raw Codex method names stay
  in bridge-local mapping code and recorded test fixtures.
- `turn/steer` must use the active `turn.id` as `expectedTurnId`, preserving the
  original `threadId`.
- `turn/interrupt` targets the active `threadId` and `turnId`.
- A completed turn does not end the room. The bridge emits `run.live.ended` when the
  Codex process or thread closes.
- Approval resolution is last and fail-closed: unknown ids are acknowledged to
  Frege as errors and never forwarded to Codex.
