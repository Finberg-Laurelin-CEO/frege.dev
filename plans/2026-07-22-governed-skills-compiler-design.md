## Problem Statement

YC's Summer 2026 RFS (operative for the Fall 2026 application cycle, deadline July 27,
2026 8:00pm PT) names "Company Brain" as a funded category. Blomfield's verbatim ask: "A
system that pulls knowledge out of all these fragmented sources, structures it, keeps it
current, and turns it into an executable skills file for AI... Then AI systems can use
that skills file to actually do the work safely and consistently. This isn't a
company-wide search or a chatbot over documents."

Frege today ships the governed store: scoped/cited context, propose → review → merge →
rollback on canonical memory, full audit trail, session capture, MCP server, local
agent. What it does not ship is the RFS's output artifact: **executable skills files**.
The problem this session solved: what exactly must be built so Frege *is* a Company
Brain in YC's terms, and in what order, given 5 days to the application deadline, a solo
founder, and Claude Code as the builder.

Joe's directive for this doc's scope: "don't worry about kismet call, founder video or
demo just worry about building it and the product and what needs to be built."

## Premises

Agreed in session (P2 revised twice, final form below):

1. **Category claim: "the governed company brain."** The defensible moat sentence is the
   five-layer integration — policy-gated writes + per-claim provenance + read/write
   audit + rollback + per-agent scoping as ONE system on agent-writable memory — plus
   the fact that the hot cohort is betting *against* human review. NOT "nobody does
   governance" (Qoris/Slite/PuppyOne falsify the naive version).
2. **Structure-first, source-agnostic.** Joe's reframe, verbatim: "we need to setup a
   structure a wireframe that is able to do what YC wants." The pipeline is the product;
   sources are adapters. Day-one adapters: captured sessions + markdown upload/paste.
   No model training anywhere; external connectors are post-submission plugins. Claude
   Code builds the full structure this week; nothing gates on external integrations.
3. **The output artifact is Agent Skills-format SKILL.md through the review gate** —
   "reviewed, cited, staleness-tracked, agent-portable skills." Compiled drafts are
   never canonical without merge approval.
4. **A plan is not traction.** This doc is engineering scope; the Jul 13 evidence
   must-haves still exist and are now owned entirely by Joe outside this doc.
5. **The competitor answer must match the verified table** (Qoris markets
   approval-gating; the application cannot pretend otherwise).

## Approaches Considered

### Approach A: Compiler Wedge (minimal viable, Codex-shaped)
One end-to-end loop on one source. Effort: S (CC ~1 day). Risk: Low. Reuses
propose/review/merge, audit ledger, MCP server, session capture. Demoable fast;
naive per-thread grouping; single source.

### Approach B: Breadth Loop (ideal architecture)
Nightly cron, Slack + Linear via remote MCP, embedding clustering, SOP pages + skills,
bitemporal columns, contradiction → supersede proposals. Effort: M (CC ~2–3 days +
review attention). Risk: Med. Full RFS coverage on paper; burns Joe's scarcest resource
(review attention) in application week; Codex's challenge lands on it.

### Approach C: Dogfood-First Compiler (creative/lateral)
Approach A with Frege/Joe's own captured sessions as source #1. Effort: S–M. Risk:
Low–Med. Instant real material, zero external dependencies; self-referential until
external material arrives.

## Recommended Approach

**Structure-first Governed Skills Compiler** — Joe's reframe of A+C: build the complete
source-agnostic structure; prove it on material already in hand (captured sessions, then
the incoming user-feedback markdown files); add external connectors as adapters later.

Build spec, in order (all behind a feature flag, all through existing governance):

1. **Skill artifact schema.** A new artifact type in the existing document/page model —
   not a parallel store. Governance metadata lives in DB columns/JSON on the artifact
   row: `scope`, per-claim `citations[]` (validated refs into sessions/documents),
   `confidence` (review-queue display only in v1 — nothing else consumes it),
   `valid_from`, `source_refs[]`, `invalidated_at`/`superseded_by` (nullable), and
   `stale_flagged_at`/`stale_reason` (nullable — set by the item-6 flag). A
   portable SKILL.md in the Agent Skills open format (consumed by Claude/Cursor/26+
   platforms) is *rendered* from the row, keeping frontmatter standard-clean; in-body
   citations use footnote-style anchors (`[^n]`) mapped to source refs. Includes the
   feature flag: a single env var `FREGE_SKILLS_COMPILER=1` checked at route and
   MCP-tool registration (~30 min — no flag infra exists today). (CC: ~2.5 hrs)
2. **Source-adapter interface.** One contract: `RawMaterial { content, provenance,
   occurred_at, source_type }`. Day-one adapters: (a) captured agent sessions (already
   in DB), (b) markdown upload/paste via a new admin-only surface (`/api/v1/materials` +
   minimal admin page) requiring provenance fields at upload: source description, author,
   date (handles the incoming feedback files). Slack, Linear, email are future
   implementations of the same interface — truthfully "pluggable," never vaporware.
   (CC: ~2.5 hrs)
3. **Compiler step.** Batch = one session or one uploaded file (v1 definition). One LLM
   pass per batch: "is there a repeatable procedure or durable fact here?" → draft
   SKILL.md with citations → **filed as a proposal into the existing
   propose/review/merge queue.** Never canonical without merge. Failure path: citation
   refs are validated before filing — proposals with unresolvable citations are never
   filed (server logs suffice for compile failures in v1); a batch with no repeatable
   procedure produces no proposal. The Compile action always returns a visible result
   summary: proposal filed / nothing found / failed. Trigger: manual "Compile" action
   only before Jul 27; nightly cron is week 2. (CC: ~4 hrs)
4. **Serving.** Approved skills exposed through the existing MCP server (list/get by
   scope, respecting existing per-key scoping so restricted skills are invisible to
   unauthorized agents), plus a rendered-SKILL.md download/copy on the admin surface so
   portability is real, not claimed (~15 min). (CC: ~2 hrs)
5. **Telemetry — the moat instrument.** Two new audit-ledger event types:
   `skill.retrieved` — fired on MCP `get` only (list does not count) — and
   `skill.corrected` with per-action payloads: edit = before/after diff; reject = full
   proposal + reviewer reason; rollback = version reverted from/to. Every correction is
   a labeled example of "what the compiler got wrong about this business" — the
   proprietary corpus from the Jul 13 moat thesis, accumulating from day one.
   (CC: ~2 hrs)
6. **One visible staleness rule.** Mechanism: during each compile pass, the LLM also
   receives **all approved skills in the batch's scope** (v1 volume is <10; the shared
   `source_refs` join is a week-2 optimization — fresh uploads have fresh refs and would
   never overlap) and answers a yes/no contradiction question per skill. On yes: set
   `stale_flagged_at`/`stale_reason` and show "stale — review suggested." Auto-filing a
   supersede proposal is a stretch goal; the visible flag alone satisfies v1. No
   autonomous edits ever. (CC: ~2–3 hrs)

Budget honestly: items sum to ~15.5 CC hrs + ~2–3 hrs local QA (the zero-regressions
criterion is nonzero work). That exceeds "1.5 days" at the margin, so the fallback below
is the *expected* path if item 6 plus QA don't fit, not an emergency valve.
Pre-authorized fallback: ship items 1–5 + QA, defer item 6; success-criteria staleness
row becomes stretch. Post-submission
(week 2): Slack adapter via official remote MCP, Linear adapter, embedding-based
clustering, richer bitemporal queries, nightly compile cron — i.e., Approach B becomes
the roadmap, not the sprint.

Explicitly rejected for this week: model training of any kind (nothing here trains a
model), external OAuth integrations, autonomous memory editing, embeddings
infrastructure.

## Success Criteria

By Jul 26, locally QA'd and feature-flagged in production without touching the
submission path:
- A captured session or uploaded markdown file can be compiled into a SKILL.md proposal
  with per-claim citations.
- That proposal appears in the existing review queue; Joe can edit, approve, reject,
  merge, roll back.
- An approved skill is retrievable by an agent through the existing MCP server under
  existing scoping; a restricted skill returns not-found to an unscoped key.
- `skill.retrieved` and `skill.corrected` events land in the audit ledger; at least one
  real correction is recorded (Joe reviewing compiled output).
- One staleness flag demonstrably fires on contradicting material (stretch if the
  pre-authorized fallback is taken).
- Zero regressions on existing auth/billing/memory paths (local QA suite passes).

## Distribution Plan

Existing deployment pipeline covers the web service and MCP server. The skill artifact
itself is distribution: Agent Skills open format means approved skills are consumable by
any compliant agent runtime without Frege-specific tooling. No new distribution surface
before submission.

## Dependencies

- Existing propose/review/merge machinery, audit ledger, MCP server, session capture —
  all reused, none rewritten.
- Feature flag for all new surface; local QA (previews broken — do not rely on preview
  deploys); production deploy only after local QA.
- No external dependencies: no new vendors, no OAuth apps, no model training.

## The Assignment

**Be reviewer #1, today.** When the first compiled SKILL.md proposal lands in your
review queue: review it, edit what's wrong, approve or reject it, and let the
`skill.corrected` event record the diff. That first correction is row #1 of the
proprietary failure corpus — the moat from your own Jul 13 thesis, finally being
captured as structured data instead of living in a text thread. Then, when the user
feedback markdown files arrive in a few days, feed them through the upload adapter and
review what the compiler proposes from *external* material. That's the behavioral test
Codex demanded, run on real users' words.
