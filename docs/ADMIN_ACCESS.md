# Admin & Platform Access — Setup and Team Onboarding

This explains how you and your team get into the Frege admin and platform
consoles today, how to create teammate accounts safely, and the plan for moving
to Google SSO restricted to `@frege.dev`.

> **Security rule:** real passwords are **never** written in this repo or pasted in
> chat. They are generated by a script, shown **once** in your terminal, and stored
> in your password manager (1Password / Bitwarden / etc.). This file documents the
> *process*, not the secrets.

---

## What the two consoles are

| URL | Who | What |
|---|---|---|
| `/admin` | Org owner/admin | Manage one organization: members, roles, API keys, models, brain, telemetry. |
| `/platform` | Platform **staff** (you) | Cross-org operations: all orgs + users, usage, approve pilot applications, activate/suspend orgs. |

`/platform` is gated by a per-user flag `users.is_platform_staff`. Only staff can
see it; everyone else is redirected to `/admin`.

## Create / reset an account (for you or a teammate)

These run from a machine with the production `DATABASE_URL`. The recommended way to
get it is `vercel env pull` into a temporary file you delete afterward.

```bash
# 1. Pull production env to a temp file (then delete it when done)
vercel pull --yes --environment=production --scope laurelin-inc

# 2a. Set or reset a password (auto-generates a strong one if you omit it)
node --env-file=./.vercel/.env.production.local \
  scripts/prototype/change-user-password.mjs teammate@frege.dev

# -> prints { "email": "...", "password": "..." } ONCE.
#    Copy the password into your password manager and share it with the
#    teammate over a secure channel (password manager share, not email/Slack).

# 3. Clean up the pulled secrets
rm -rf .vercel
```

> The teammate must already exist as a `users` row to reset their password. To create
> a brand-new teammate from scratch, either invite them into an org from `/admin`
> (Members → invite) and have them set their own password via the invite link, or ask
> the engineer to add the user row. The invite flow is the cleanest path for new people.

### Make a teammate a platform staff operator
Only do this for people who should see **all** orgs and usage.

```bash
vercel pull --yes --environment=production --scope laurelin-inc

node --env-file=./.vercel/.env.production.local \
  scripts/prototype/set-platform-staff.mjs teammate@frege.dev
# revoke with: ... set-platform-staff.mjs teammate@frege.dev --revoke

rm -rf .vercel
```

Or, if `DATABASE_URL` is already set in your shell:
```bash
pnpm user:staff teammate@frege.dev
```

## Recommended team setup (do this once)

1. Decide who needs **platform staff** (probably just you + co-founders) vs. who
   only needs **org admin** access to a specific org.
2. For each person:
   - Create their account (invite flow or password script).
   - Grant platform staff only if they need cross-org visibility.
   - Store their credential in the shared **company password manager vault**, not here.
3. Turn on 2FA at the password-manager level for everyone.
4. Rotate the `joe-test@frege.dev` QA account's password (it's been used in testing)
   and keep it for smoke tests only.

## Planned: Google SSO restricted to @frege.dev

You asked for "very good OAuth" — sign in with Google, only for `@frege.dev`
addresses. That's the right end state. It's a real feature (provider registration +
callback routes + account linking), so it's scheduled as its own piece of work. When
we build it, the shape will be:

### How it will work
- Use **Auth.js (NextAuth)** with the **Google provider**. This is the standard,
  well-audited choice for Next.js on Vercel and supports a domain restriction.
- Restrict to your domain in two layers:
  1. In the Google Cloud OAuth consent screen, set the app to **Internal** for the
     `frege.dev` Google Workspace (only Workspace members can authorize).
  2. In an Auth.js `signIn` callback, reject any email that doesn't end in
     `@frege.dev` (defense in depth, and covers the case where the Workspace isn't
     the auth boundary).
- Keep the existing email+password path as a fallback for accounts that aren't on
  the Workspace (e.g. external pilot owners), or retire it for staff-only access.

### What you'll need to provide when we build it
All set in Vercel env (never in repo):
- `AUTH_SECRET` — random string (`openssl rand -base64 32`). On Vercel you do **not**
  need `NEXTAUTH_URL`; production URL is auto-detected.
- `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` — from a Google Cloud OAuth 2.0 client.
- Google Cloud setup: create an OAuth 2.0 Client (type: Web), add authorized redirect
  URI `https://frege.dev/api/auth/callback/google`, and set the consent screen to
  **Internal** under the frege.dev Workspace.

### Why it's deferred
Wiring Auth.js touches the session/login system that the admin, platform, billing,
and API-key flows all depend on. It deserves its own focused change + testing rather
than being bolted on alongside billing. The email+password path above is secure for
now if credentials live in a password manager with 2FA.
